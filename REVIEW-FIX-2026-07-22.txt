!! POST-BATCH CORRECTION — ITEM 1 SHIPPED A SILENT ANDROID REGRESSION !!
───────────────────────────────────────────────────────────────────────────
Found by independent verification review of this batch (2026-07-22, same
day). Item 1's exclusion list contained `<dir>src`, whose stated premise —
"index.html only loads dist/ bundles, so assets/src/ is a dead dev tree" —
was TRUE but INCOMPLETE. index.html's own tags are not the whole runtime
surface: src/data/translations.js INJECTS scripts at runtime,

    script.src = 'src/data/bible-' + code + '.js'     (9 translations)
    script.src = 'src/data/bible-studies.js'          (Bible Studies)

so `<dir>src` removed ~36 MB of LIVE data from the APK. Nothing failed
loudly — the loader's onerror resolves — so on Android:
  • every non-default translation silently fell back to NKJV, including
    the owner's NKJV-R and KJV-R restored-name editions;
  • Bible Studies dead-ended on its "Try again" affordance.
PROVEN by building the APK and listing it: 36 asset entries / 11.3 MB with
ZERO bible-*.js present. The batch's measured numbers were exactly right;
only the "dead" classification was wrong. The genuine dead weight is
~13 MB, not ~51 MB.

FIX (2026-07-22): `<dir>src` replaced by explicit exclusions — the
bundle-only source dirs (components/hooks/renderer/search/stores/styles/ui
+ app.jsx) and the src/data files build.py concatenates into dist/ (books*,
matthew*, the VOT corpora, the ES modules). The ten runtime-injected files
are KEPT. Re-verified by rebuild: 76 asset entries / 48.8 MB, all ten
present, all dead weight still excluded.

RECURRENCE GATE: tools/check-apk-assets.js parses the runtime `script.src`
injections out of the assets tree, applies aapt's basename-matching rules
to ignoreAssetsPatterns, and FAILS if any runtime-injected asset would be
excluded. Wired into the pre-commit hook (Step 5c) + `npm run
check:apk-assets`. RED-proven: reinstating `<dir>src` makes it list all ten
files and exit 1.

LESSON: an asset is not dead because index.html doesn't name it. Dynamic
`script.src` injection is a first-class runtime surface, and a loader that
degrades gracefully (onerror → fallback) turns a packaging mistake into a
SILENT feature loss rather than a crash.

ITEM 1 — APK shipped ~51 MB of dead assets                    STATUS: DONE
Finding (build-output forensics on the signed APK): the packaged assets/
carried the entire dev ES-module source tree assets/src/ (283 files incl.
77 *.test.*, unminified JSX), four root files whose contents are already
concatenated into dist/bundle-a.js (app.css, react.min.js, react-dom.min.js,
search-data.js), service-worker.test.js, and a Windows shortcut junk file
"index.html - Shortcut.lnk". Nothing at runtime reads any of it —
index.html only loads dist/ bundles.
Fix (app/build.gradle.kts): androidResources { ignoreAssetsPatterns += … }
(AGP 9 DSL): "<dir>src", "*.lnk", "*.test.js", "app.css", "react.min.js",
"react-dom.min.js", "search-data.js". Two gotchas handled + recorded in the
kts comment block: (a) supplying ANY pattern REPLACES aapt's built-in
default ignore set, so the defaults (gDefaultIgnoreAssets) are re-declared
verbatim first; (b) patterns are aapt-syntax matched on each entry's
BASENAME case-insensitively, so "app.css" is exact and cannot hit
dist/app.min.css, and "*.test.js" has no match under dist/. assets/ is
shared with the PWA, so the files STAY in the repo — this is purely a
packaging exclusion. Both .lnk files deleted from the tree.
Verified (real build, agent-run): assembleDebug APK = exactly 36 asset
entries, ~11.3 MB, ZERO from the excluded set; dist/, index.html,
service-worker.js, fonts/icons/images all retained.

ITEM 2 — readUriAsBase64 trusted provider-declared size       STATUS: DONE
Finding: StorageManager.readUriAsBase64 checked the provider-DECLARED size
(OpenableColumns.SIZE) against maxBytes, then read the stream with an
UNBOUNDED readBytes(). A buggy/malicious provider can declare small and
stream gigabytes → heap OOM on the import path.
Fix: the actual read now routes through the existing readBounded(input,
maxBytes) — the cap is enforced on the bytes REALLY pulled, not just the
declared number. An over-delivering stream returns Failure("too_large"),
the same reason the declared-size check uses, so the JS side sees ONE
failure mode.
Test (StorageManagerTest): regression with a LYING provider (declares
under-cap, streams over-cap) → "too_large". RED-first.

ITEM 3 — finishV3Export leaked the partial backup on flush throw  STATUS: DONE
Finding: StorageManager.finishV3Export deleted the partial document on the
abort / incomplete-frame paths, but if flush()/close() THREW at commit,
the bytes already written stayed on disk — a truncated, misleading-looking
.votbak that would only fail at import time (the only-backup must fail
clean).
Fix: the commit path's catch now runs deleteDocumentQuietly(uri) too —
same cleanup contract as the abort paths.
Test (StorageManagerTest): forces a flush-time throw, verifies the delete.
RED-first.

ITEM 4 — GardenImageCache.download unbounded on chunked responses  STATUS: DONE
Finding: MAX_DOWNLOAD_BYTES was enforced only against the declared
Content-Length; a chunked (-1) response read unbounded into the heap.
Fix: new readCapped() streams with a running byte counter and fails CLOSED
(cache miss) the moment the cap is passed — no reliance on the server
telling the truth.
Tests (GardenImageCacheTest): chunked over-cap rejected; under-cap payload
intact. RED-first.

ITEM 5 — back-press contract compared one encoding only       STATUS: DONE
Finding: MainActivity's handleAndroidBack contract compared the
evaluateJavascript result against "\"true\"" only. evaluateJavascript
JSON-encodes the JS return value, so the SAME logical answer arrives in two
shapes — JS string "true" → `"true"` (quoted), JS boolean true → `true`
(unquoted). A JS refactor to a bare boolean would SILENTLY break the
contract: the app would quit on back presses JS actually consumed.
Fix: extracted MainActivityLogic.isBackPressConsumed(result) accepting both
encodings; everything else ("false" either shape, "null" when the handler
is missing, Kotlin null) = not-consumed.
Tests (MainActivityLogicTest): 6 boundary cases. RED-first.

ITEM 6 — splash could stick forever                           STATUS: DONE
Finding: splash dismissal depended SOLELY on onPageFinished; a main-frame
load error would hold the splash indefinitely.
Fix: an onReceivedError override releases the hold for MAIN-FRAME errors
only (subresource errors never release). Safety hatch — bundled assets
make a main-frame error near-impossible in practice.

ITEM 7 — double saveToFile clobbered pendingExportContent     STATUS: DONE
Finding: a second saveToFile launch while the first picker was still open
overwrote pendingExportContent — the FIRST picker's result would then write
the SECOND export's payload.
Fix: pendingExportContent now doubles as the in-flight guard: a re-launch
while non-null is refused and surfaces error:busy through the existing JS
error contract; launch() itself is wrapped in try/catch →
error:launch_failed (a picker that can't open no longer strands the
payload).

ITEM 8 — screenshot pipeline recycled bitmaps only on the happy path  STATUS: DONE
Finding: the tab-thumbnail screenshot pipeline recycled its bitmaps inline
on success only; any exception mid-pipeline leaked every allocation.
Fix: a finally-block recycles each DISTINCT allocation — identity-compared
(it !==) because createBitmap/scale may return the SOURCE instance — so
each real allocation is recycled exactly once on ALL paths.

ITEM 10 — per-keystroke full vot-state persist                STATUS: DONE
Finding: every search keystroke triggered a full vot-state JSON.stringify +
IndexedDB put + LS shim write — searchQuery is a tabField riding the FULL
persist chain, with no debounce or coalescing anywhere.
Fix (hooks/use-persisted-state.js — at the usePersistedState SINK, the one
place all persist effects funnel through):
  1. TRAILING-EDGE 250 ms COALESCING — rapid unions inside the window
     coalesce to ONE StateStore.set carrying the LATEST union (each new
     union resets the window). Safe because StateStore.set is
     FULL-REPLACEMENT with no live readers between writes: intermediate
     unions were never observable, so latest-union-wins loses nothing.
  2. GUARANTEED FLUSH — a pending union is written SYNCHRONOUSLY on
     visibilitychange→hidden, pagehide, beforeunload, and unmount. No
     union that reached the hook is ever dropped on background/close.
  3. BOOT-CRITICAL BYPASS — theme / fontStyle / fontScale (read
     synchronously from the LS shim by the index.html boot script,
     index.html:73) write IMMEDIATELY, superseding (not dropping) any
     pending debounced union.
  4. The initial mount write stays immediate (unchanged boot contract).
Deliberately NOT in CachedStore._save: that would entangle the hydration
state machine and the navigator.locks 3-way merge — the coalescing lives
at the hook sink where none of that machinery can be disturbed.
Tests: NEW use-persisted-state.test.js, 15 tests; all hydration / rebase /
merge suites green; full suite 2758 → 2787.

ITEM 11 — v3ImportReadChunk "no ceiling"          STATUS: ADJUDICATED (2026-07-22)
The review OVERSTATED it. The chunk allocation is
minOf(maxBytes, importFrameRemaining) and the SOLE caller passes a constant
512 KB chunk size, so the frame loop can never inflate allocation — the
"unbounded" premise requires a caller that doesn't exist. No fix; the
ceiling is already structural. Recorded so the finding isn't re-raised.

ITEM 14 — export could miss a union inside the 250 ms debounce window
                                            STATUS: DONE (2026-07-22)
Finding: a vot-state change made within 250 ms of tapping Export could be
silently missing from that backup — the app's ONLY backup mechanism (U1).
Root cause: the persist sink's trailing-edge debounce holds the latest
union in a ref without calling StateStore.set, while the v3/v2 export
reads vot-state straight from IndexedDB after a whenSaved() durability
barrier; since no write had been initiated, the barrier had nothing to
await and the IDB read returned the pre-debounce union. (Flagged as the
one accepted risk by the independent verification review of this batch.)
Fix: usePersistedState publishes its existing flush as
window.__flushPersistState for the life of App() — a window bridge, not a
module export, because bundle-b/bundle-d are separate esbuild IIFEs and
module-scope registrations don't cross — and both export drivers in
SettingsScreen call it synchronously before buildV3Manifest, so the
existing whenSaved() barrier awaits the flushed write before the manifest
snapshots IDB. No-op when idle, clears the pending timer (no duplicate
write), boot-critical immediate path untouched. Bridge registered in
BRIDGES.md section 11.
Verification: RED-first — pre-fix the exported manifest's vot-state
dropped the pending union (searchQuery undefined); post-fix targeted
suites pass and the full suite is 2792/2792, including an end-to-end
test mounting the real hook against the real StateStore + fake IDB,
driving the exact export sequence without advancing the debounce timer.
Commit d1cc7f2.
