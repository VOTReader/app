(A) TAB THUMBNAILS vs THEME SWITCH — owner: mixed dark/light cards after a
theme change. v1 (invert-filter + theme metadata) shipped first; owner
device-tested it: "pretty convincing" BUT hero hues drifted blue (the
filter is an approximation) and pre-update legacy cards didn't participate
(his Library card stayed dark). He proposed remembering BOTH theme states —
implemented as v2 the same day: native capture can only shoot the on-screen
theme, but html2canvas renders from a DOM CLONE, so the new
PlatformBridge.takeThemedScreenshot forces the opposite theme class on the
clone (onclone) and renders the other theme invisibly (works on Android
too — html2canvas is in the same JS bundle). Entries are variant maps
{dark?, light?, unknown?}: primary capture fills the current slot; a
~900ms-deferred themed render fills the other (seq-guarded, overview-
suppressed); TabsOverview picks the matching variant → theme flips are
INSTANT lookups with true pixels; the invert filter remains only as a
transitional fallback; classifyThumbTheme (luminance probe) upgrades
legacy `unknown` rows so old cards participate too; garden = one capture
fills both slots. Live-proven: app stayed dark → row {dark 82KB, light
72KB}, luma 2 vs 239; overview served each theme's variant unfiltered.
(A2, owner re-test) TABS-SCREEN HOME BUTTON DEAD + PC BLANK THUMBNAILS —
(1) the overview's HomeBtn called __goHome, which changes the screen UNDER
the overlay (looked like a no-op on both platforms). HomeBtn gained a
`beforeGo` prop; the overview passes its own dismiss. (2) html2canvas
occasionally yields a ZERO-SIZED canvas (boot races); its toDataURL is
"data:," — truthy, so it was STORED and painted that tab card permanently
blank (background tabs never recapture → the owner's PC wall of blank
squares). Fixed at three layers: webTakeScreenshot rejects tiny canvases +
sub-1000-char encodes ('' = failure, next capture retries); mergeVariant
floors incoming URLs; the load-on-mount SCRUBS stored degenerate variants
(drops the field, deletes emptied rows → placeholder until the next good
capture heals it). Live-proven: seeded {dark:'data:,',light:'data:,'} row
deleted at boot; overview Home tap closes the overlay + lands Home.
(A3, owner re-test: PC STILL blank; Android fine) — local repro is healthy
(reading-screen captures 110KB primary + 102KB themed, ~750ms each), so the
PC failure is ENVIRONMENTAL (prime suspect: an extension injecting body
nodes that make html2canvas throw, or canvas-read blocking; extensions run
in installed PWAs too — matches PWA+site failing while Android's native
path works). Hardened 3 ways: (1) capture targets #root, not document.body
— extension junk is body-level, so it can no longer break the render (also
excludes body-portaled sheets from cards); (2) a 16×16 uniformity probe
rejects blank renders (luma range <6 → '' — real screens carry text
contrast; also catches canvas-blocker white-outs at the store level);
(3) every web-capture failure now traces via _thumbFail → console.warn
"[thumb] …" + DiagnosticLog('thumb'). If the owner's PC still shows
placeholders after this build: F12 → Console → send the [thumb] lines —
they name the exact cause.
(B) EXCERPT-PICKER "can't save until I scroll" — the picker only captured
selection on mouseup/touchend over the body, but Android's long-press
selection delivers its touchend NON-BUBBLING (same WebView behavior as the
tab-drag lockup) and HANDLE drags fire no page touch events at all — a
later scroll's touchend was what finally ran the capture. Fixed: document
'selectionchange' listener (150ms debounce) drives the state commit; touch/
mouse handlers stay as fast path. Live-proven: programmatic Selection.addRange
(fires ONLY selectionchange) flipped the footer to "Insert this excerpt".
PREVIEW GOTCHA: hidden-tab setTimeout clamps to ~1s — sample AFTER generous
settles or the 150ms debounce looks broken.
